## What Claude Projects are, in one paragraph

A project is a goal + a repo + settings (instructions, model, connectors). The **main chat is a coordinator**: you
brief it and it routes work into **threads**. Each thread is a separate Claude Code session on **its own branch and
copy of the repo**; threads run in parallel, conflicts are ordinary merge conflicts, and each thread reports back to the
coordinator. The project has **shared memory** (decisions, reasons, who to ask, how you like updates), a **library**
(files you added + artifacts Claude made), an **Overview** of what is in flight, and per-project usage with separate
model/effort for the coordinator and for threads.

## What main already has (after #31)

- **A room is Chat or Work.** Chat has no project: its files go to a private materials folder
  (`<rooms>/<id>/materials`). Work connects a project: a folder, a new folder or a worktree. README:
  "`agoryx new "Task" --mode work` creates a project, and `--dir PATH` uses an existing one". `agoryx new` without
  `--dir`/`--mode work` is now Chat.
- **The room remembers its project.** `RoomState.project: RoomProject` = `{ workspace, createdWorkspace, worktree?,
  doc? }` (`internal/agora/types.ts`). It is kept across Work → Chat → Work. The switch is `room.mode.changed`
  (human only, between runs). It resets `sessions`, `cursors` and `profiles`, so every agent starts a fresh session
  with a full briefing (`internal/agora/projection.ts`, `changeRoomMode` in `service.ts`).
- **No automatic commits.** Runs leave private recovery snapshots (`refs/agoryx/checkpoint/…`), never on the working
  branch. The briefing no longer tells agents to commit steps. `BRIEFING_VERSION` (`prompts.ts:1`) forces one fresh
  session when the briefing changes in a way that must reach old sessions.
- **The sidebar** groups by `groupKey` = Chat → "Chats", otherwise `folder` (the worktree source for worktrees)
  (`ui/src/components/Sidebar.tsx:202`). The sidebar can be collapsed.

So "project" already means **the Work folder of a room**. This plan does not add a second meaning. It gives that
folder a goal, instructions and memory that outlive one room.

## What Agoryx takes, and why

- **Evolution of the room, not a wrapper.** The value is in what the agents know when a Work room starts: the
  project's instructions and memory reach them. Today every room starts from zero, and settled items, decisions and
  open disagreements on a room's table die with it.
- **Memory keeps edges, not only nodes.** Besides decisions it keeps **unresolved disagreements with both positions**
  and who held them. Claude Projects has one voice and so cannot keep this.
- **Memory must not feed polite convergence.** Decisions placed in every briefing are a ready mechanism for an early
  pass. So the index lists open disagreements first, and every entry is rendered as someone's claim with its reason
  ("codex, D2 in room X: … because …"), never as a room fact.
- **The project key is the folder.** `key = project.worktree?.source ?? project.workspace`, the same key the sidebar
  uses. A worktree room (`<agoraHome>/worktrees/<repo>-<id>`) belongs to its source folder's project. Membership is
  derived, not stored: a room has no new field, and data written for a folder applies to every Work room in it,
  past and future.
- **Nothing is auto-written.** Project data exists once someone writes a goal, instructions or a memory entry. An
  empty project adds only one line to a Work briefing (how to write memory). No goal is taken from a chat line.
- **Chat has no project memory.** A Chat room gets none of this, even if it remembers a project. After a switch to
  Work, the fresh briefing carries it.
- **No coordinator** (decision 1). No main room, no routing role. Every room in a project is equal. Any participant can
  start a thread from any Work room. Agoryx runs the command and shows the result; it does not route work.
- **Threads mostly exist already.** `agoryx new --dir D --worktree -m "<brief>"` makes a Work room on `agoryx/<slug>`,
  and an agent can run it from a turn (`createdBy`, `internal/agora/daemon.ts:1283`). What is missing is the link to
  the parent and the report back. Threads wait for a dogfooding signal.

## Decisions (Ivan, 2026-10-02)

1. **Coordinator: none.** No main room and no coordinator role.
2. **Thread roster: the spawner always chooses it explicitly.** The default is one agent, with the other reviewing the
   diff in the room that spawned the thread.
3. **Existing data: no migration.** There are no users.
4. **Memory lives in `agoraHome`.** That keeps the repo clean and gives every worktree the same copy.

## Data model

```
<agoraHome>/projects/<keyHash>/
  project.json        { key, name?, goal?, instructions?, threadDefaults?{agents, model, effort} }
  events.jsonl        project.changed | memory.noted | memory.revised | memory.removed   (each with by)
  MEMORY.md           rendered from the memory events; a human edit = memory.revised with by
```

- `keyHash` = a short hash of the absolute key path. `key` is stored, so a moved folder can be re-pointed by hand.
- New code goes in `internal/agora/projects.ts` and `internal/agora/memory.ts`. The legacy `internal/memory`
  (MemoryService, its own `MEMORY.md` renderer, consolidation, the old `agoryx chat` engine) is neither reused nor touched.
- `RoomSummary` gets a derived `projectName?` (when the folder has one) for the sidebar. Rooms get no stored field.
- A memory entry: `{ id, kind: decision|fact|disagreement|person|preference, text, why?, positions?, source: {room,
  tableRef?}, by, at }`.
- **A position** (for `disagreement`) is assembled from the table, since it has no such field: for an open question,
  each open option (`TableOption` with `q`) with its author, plus its standing objections (`TableNote` kind `object`,
  the `contested` computation in `internal/agora/table.ts`), all verbatim.

## How it reaches the agents

`buildDelta` (`prompts.ts:469`) only renders the room's own events (`store.since(…)`, `engine.ts:1663`), and project
events live in another log. The plan uses the mechanism the human profile already has (`state.profiles[agent.id]`,
`engine.ts:1656`):

- The room records, per agent, the hash of the project data that agent was given (a `projectSeen` map next to
  `profiles`, reset by `room.mode.changed` like `profiles`).
- A fresh session in Work gets, in `buildBriefing` (`prompts.ts:265`, Work branch only): the goal, the instructions,
  the memory path and a capped index (disagreements first), plus one line on `agoryx memory note|promote`.
- A running session gets only what changed since its last turn, as one line in the delta ("memory: +1 disagreement by
  codex — `agoryx memory` for the text").
- `BRIEFING_VERSION` is **not** bumped for this: the delta line covers old sessions without replaying the history.
- Instructions stay short: agents already read the repo's CLAUDE.md/AGENTS.md, and the briefing is already long.

## CLI (agents have the same hands as the human)

```
agoryx project [--dir D]                         # the current room's project, or D's
agoryx project set goal|instructions|name "<text>" [--dir D]
agoryx memory | memory note "<text>" [--kind …] [--why …] | memory promote S3|D2|Q1 | memory remove <id>
# threads (step 4):
agoryx new --from <room> --worktree --agents '…' -m "<brief>"   # Work; dir = the parent's project key
```

Without `--dir`, the commands use the room of the calling agent (its key). In a Chat room they refuse: "no project
connected". Every write records `by`.

## Threads (steps 4–5)

- A thread is a Work room made by `agoryx new --from <room> --worktree`: the dir defaults to the parent's key, and
  `parent` is recorded on `room.created`. A parent in Chat is refused.
- When its run ends, the parent gets `thread.reported` as a projection, with no summary: the thread's last message
  verbatim, its new table items by id, its branch, and the diff stat of the branch against its base **plus uncommitted
  changes**. Agents now commit only when they choose to, so the uncommitted part is part of the result.
- **It wakes the agent who spawned the thread** (`createdBy`). If the human spawned it, it wakes no one and shows in
  Attention.
- Steering = `agoryx say --room <thread>` or typing in the split. Merging is the agents' own git/PR work.
- UI as in the screenshot: a thread card in the parent's feed (title, roster, branch + diff stat, file chips, first open
  question, *View thread*), and the thread as an ordinary `Room` in the right split with a `Threads › <title>`
  breadcrumb, nested under its parent in the sidebar.

## UI

- **Sidebar:** in `groupRooms`, a folder group whose folder has project data shows `projectName` (or the folder name)
  with a project icon. Clicking the group head opens the project page. Chats stay as they are.
- **Project page** (`{ kind: "project"; key }` added to `Route`, `ui/src/lib/store.ts:54`): name, goal, instructions,
  memory grouped by kind with disagreements first, and the folder's rooms. Editing reuses the autosave + 409 conflict
  from the T3 editor.
- **Start screen / mode switch to Work:** when the chosen folder already has project data, show its name and goal
  under the folder picker. There is no separate "make a project" step.
